==Какие типы баз данных вы знаете? В чем их основные отличия?== 
### 1. Реляционные базы данных (SQL)

- **Суть:** Данные хранятся в строго определенных таблицах (строки и столбцы), которые связаны между собой.
- **Структура данных:** Таблицы со связями (relations).
- **Ключевые особенности:**
    - **ACID:** Гарантии транзакций (Atomicity, Consistency, Isolation, Durability). Либо вся операция выполнена, либо ничего не изменилось. (также не часто, но есть у реляционных)
    - **Строгая схема (Schema-on-write):** Структура таблицы (колонки, типы данных) задается заранее и не меняется.
    - **Язык запросов:** SQL (Structured Query Language).
    - **Вертикальное масштабирование:** Увеличение мощности одного сервера (CPU, RAM).
- **Когда использовать:** Финансовые системы, банковские приложения, системы учета, e-commerce — везде, где целостность данных важнее скорости и гибкости.
- **Примеры:** **PostgreSQL**, **MySQL**, Oracle, MS SQL Server.

### 2. Нереляционные базы данных (NoSQL)

Это целая группа разных баз данных. Вот четыре основных типа:
#### 2.1. Документо-ориентированные (Document)

- **Суть:** Хранят данные в виде документов, похожих на JSON-объекты. Один документ содержит всю информацию о сущности.
- **Структура данных:** Коллекции документов (JSON/BSON).
- **Ключевые особенности:**
    - **Гибкая схема (Schema-on-read):** Документы в одной коллекции могут иметь разный набор полей.
    - **Легкое горизонтальное масштабирование:** Просто добавить новые серверы.
    - Нет сложных JOIN-ов (данные обычно вложены друг в друга).
- **Когда использовать:** Профили пользователей, каталоги товаров, контент-менеджмент (статьи, блоги).
- **Примеры:** **MongoDB**, Couchbase.
#### 2.2. Ключ-Значение (Key-Value)

- **Суть:** Самая простая модель. Данные хранятся как в словаре: есть уникальный ключ и есть значение.
- **Структура данных:** Огромная хэш-таблица.
- **Ключевые особенности:**
    - **Максимальная скорость:** Невероятно быстрые операции чтения и записи по ключу.
    - **Простота:** Легко использовать и понимать.
    - Часто работают в оперативной памяти (in-memory) для еще большей скорости.
- **Когда использовать:** Кэширование, хранение сессий пользователей, игровые таблицы лидеров.
- **Примеры:** **Redis**, Memcached, DynamoDB.
#### 2.3. Колоночные (Wide-Column / Column-Family)

- **Суть:** Данные хранятся не по строкам, а по колонкам. Это позволяет очень быстро считывать и агрегировать данные из определенных колонок.
- **Структура данных:** "Семьи колонок" (группы связанных колонок).
- **Ключевые особенности:**
    - **Оптимизированы под запись:** Идеальны для систем, куда непрерывно поступает огромный поток данных.
    - **Высочайшая доступность и отказоустойчивость.**
    - Отлично масштабируются горизонтально.
- **Когда использовать:** Big Data, аналитика, IoT (данные с датчиков), логгирование, хранение временных рядов (time-series).
- **Примеры:** **Apache Cassandra**, ScyllaDB, HBase.
#### 2.4. Графовые (Graph)

- **Суть:** Созданы для хранения данных в виде узлов (вершин) и связей (ребер) между ними.
- **Структура данных:** Узлы и связи с их свойствами.
- **Ключевые особенности:**
    - **Оптимизированы для поиска связей:** Мгновенно находят пути, друзей друзей, общие интересы.
    - Интуитивно понятная модель для сильно связанных данных.
- **Когда использовать:** Социальные сети, рекомендательные системы ("пользователи, купившие этот товар, также купили..."), антифрод-системы (поиск мошеннических схем).
- **Примеры:** **Neo4j**, Amazon Neptune.

==Что такое ACID свойства транзакций?== 

**ACID** — это набор из четырех свойств, которые гарантируют надежность транзакций в базе данных.

### A — Atomicity (Атомарность)

- **Суть:** **"Всё или ничего".**
- **Объяснение:** Транзакция — это неделимая операция. Либо все её шаги выполняются успешно, либо, в случае сбоя, система откатывается в состояние, как будто транзакция и не начиналась.
- **Пример:** При переводе 100 р. со счета А на счет Б должны произойти два действия: списание с А и зачисление на Б. Атомарность гарантирует, что не случится ситуации, когда деньги с А списались, а на Б не зачислились.
### C — Consistency (Согласованность)

- **Суть:** **"Данные всегда корректны".**
- **Объяснение:** Транзакция переводит базу данных из одного целостного (валидного) состояния в другое. Ни одна транзакция не может нарушить установленные правила и ограничения (constraints).
- **Пример:** Если на счете А всего 50 р., система не должна позволить перевести 100 р. Согласованность гарантирует, что правило "баланс не может быть отрицательным" будет соблюдено.
### I — Isolation (Изолированность)

- **Суть:** **"Параллельные транзакции не мешают друг другу".**
- **Объяснение:** Результаты одной выполняющейся транзакции не видны другим, пока она не будет завершена. Для каждой транзакции создается иллюзия, что она работает с базой данных в одиночку.
- **Пример:** Пока идет наш перевод, другая параллельная транзакция (например, подсчет общей суммы денег в банке) не увидит промежуточное состояние, когда 100 р. "повисли в воздухе". Она увидит состояние либо до перевода, либо после.
### D — Durability (Долговечность)

- **Суть:** **"Что записано, то не пропадет".**
- **Объяснение:** Если транзакция успешно завершена (committed), ее результаты сохраняются навсегда и не будут потеряны даже в случае сбоя системы (например, отключения питания).
- **Пример:** Как только система сообщила "Перевод выполнен", можно быть уверенным, что изменения надежно записаны на диск. Даже если сервер сразу после этого перезагрузится, деньги останутся на счете Б.

==Что такое нормализация базы данных? Зачем она нужна? Опишите нормальные формы.==
**Нормализация** — это процесс организации данных в реляционной базе данных для устранения их **избыточности** (дублирования) и **зависимостей**.

Проще говоря, это приведение таблиц к "правильному" виду, когда каждая часть информации хранится только в одном месте.
всего нормальных форм ~8, но на практике достаточно первых 3-х
#### 1. Первая нормальная форма (1НФ)

- **Правило:** **Все значения должны быть атомарными.** В одной ячейке не может быть списка или набора значений.
#### 2. Вторая нормальная форма (2НФ)

- **Требование:** Таблица должна быть в 1НФ.
- **Правило:** **Все поля должны полностью зависеть от всего первичного ключа, а не только от его части.** Это правило актуально для **составных ключей**.

#### 3. Третья нормальная форма (3НФ)

- **Требование:** Таблица должна быть в 2НФ.
- **Правило:** Все атрибуты зависят только от первичного ключа, а не от других атрибутов (нет транзитивных зависимостей).

==Что такое индексы в базе данных? Как они работают? Какие типы индексов вы знаете?==

**Индекс** — это специальная структура данных (чаще всего B-дерево), которая хранит отсортированную копию значений одного или нескольких столбцов таблицы и указатели на соответствующие им строки. Его основная задача — **резко ускорить операции поиска и выборки данных (SELECT)**. При этом замедляются операции записи (INSERT, UPDATE, DELETE), так как при каждом изменении БД приходится обновлять связанные с ней индексы.

### Как они работают (на примере B-дерева)?

1. Когда вы создаете индекс, например, по столбцу username, база данных строит сбалансированное дерево (B-Tree).
2. В "листьях" этого дерева хранятся отсортированные значения username и указатели (адреса) на физическое расположение строк с этими именами в таблице.
3. Когда поступает запрос SELECT * FROM users WHERE username = 'anna', СУБД не сканирует всю таблицу users.
4. Она обращается к индексу, быстро находит 'anna' в отсортированном дереве (поиск по дереву — очень быстрая операция, O(log n)) и получает точный "адрес" нужной строки.
5. Затем она напрямую считывает эту строку с диска.

#### 1. Кластерный (Clustered)

- **Суть:** Физически упорядочивает строки таблицы на диске в соответствии со значением индексированного столбца.
- **Аналогия:** Словарь. Слова (ключ) отсортированы по алфавиту, и их определения (данные) находятся сразу же за ними.
- **Ключевые свойства:**
    - Может быть **только один** на таблицу.
    - Обычно автоматически создается для PRIMARY KEY.
    - Обеспечивает самый быстрый доступ к данным, особенно для диапазонных запросов (например, WHERE id BETWEEN 100 AND 200).
#### 2. Некластерный (Non-Clustered)

- **Суть:** Создает отдельную структуру, которая хранит отсортированные значения ключа и указатели на строки данных. Сами данные в таблице остаются в произвольном порядке.
- **Аналогия:** Тот самый предметный указатель в книге. Указатель отсортирован, а сами страницы в книге — нет (относительно тем из указателя).
- **Ключевые свойства:**
    - Может быть **много** на одну таблицу.
    - Это самый распространенный тип индексов, который создается вручную.
#### 3. Уникальный (Unique)

- **Суть:** Это некластерный индекс, который дополнительно гарантирует, что все значения в индексированном столбце (или комбинации столбцов) являются уникальными.
- **Применение:** Используется для столбцов, которые должны быть уникальными, но не являются первичным ключом (например, email или номер телефона).
#### 4. Составной (Composite / Compound)

- **Суть:** Индекс, построенный сразу по нескольким столбцам.
- **Применение:** Ускоряет запросы, которые фильтруют данные по нескольким полям одновременно. Например, для запроса WHERE last_name = 'Иванов' AND first_name = 'Иван'.
- **Важный нюанс:** **Порядок столбцов** в составном индексе имеет огромное значение. Индекс по (last_name, first_name) будет эффективен для поиска по last_name и для поиска по last_name + first_name, но бесполезен для поиска только по first_name.
#### 5. Полнотекстовый (Full-Text) 

- **Суть:** Специализированный индекс для поиска слов и фраз внутри больших текстовых полей (TEXT, VARCHAR).
- **Применение:** Реализация поиска по статьям, описаниям товаров, документам. Он умеет работать с морфологией, стоп-словами и релевантностью.

==В чем разница между кластерным и некластерным индексом?==
Основное отличие в том, что **кластерный индекс — это сама таблица, физически отсортированная на диске**, поэтому он может быть только один. А **некластерный индекс — это отдельная, компактная структура с указателями на данные**, поэтому их может быть много.

Кластерный индекс обеспечивает самый быстрый доступ к данным, так как не требует дополнительных переходов. Некластерный — это компромисс, позволяющий ускорить поиск по разным столбцам ценой дополнительного места на диске и небольшого замедления операций записи.

==Опишите основные команды SQL: SELECT, INSERT, UPDATE, DELETE.==
### 1. SELECT

- **Назначение:** **Читает** или извлекает данные из одной или нескольких таблиц. Это самая часто используемая команда.
- **Базовый синтаксис:**
    
    ```sql
    SELECT column1, column2, ...
    FROM table_name
    WHERE [условие];
    ```
- **Пример:** Выбрать имена и email всех активных пользователей.
    
```sql
SELECT username, email
FROM Users
WHERE status = 'active';
```  


- **Ключевые слова:**
    
    - SELECT *: Выбрать **все** столбцы.
    - FROM: Указывает, из какой таблицы брать данные.
    - WHERE: **Фильтрует** строки по заданному условию.
    - ORDER BY: **Сортирует** результат (например, ORDER BY username ASC).
    - GROUP BY: **Группирует** строки для использования агрегатных функций (например, COUNT(), SUM()).
### 2. INSERT
- **Назначение:** **Создает** новые записи (строки) в таблице.
- **Базовый синтаксис:**

    ```sql
    INSERT INTO table_name (column1, column2, ...)
    VALUES (value1, value2, ...);
    ```
- **Пример:** Добавить нового пользователя в таблицу Users.

    ```sql
    INSERT INTO Users (username, email, registration_date, status)
    VALUES ('anna', 'anna@example.com', '2023-10-27', 'pending');
    ```
- **Ключевые слова:**
    - INTO: Указывает, в какую таблицу добавлять данные.
    - VALUES: Содержит значения для добавляемых столбцов. Порядок значений должен соответствовать порядку столбцов.
### 3. UPDATE

- **Назначение:** **Изменяет** существующие записи в таблице.
- **Базовый синтаксис:**
    ```sql
    UPDATE table_name
    SET column1 = value1, column2 = value2, ...
    WHERE [условие];
    ```
- **Пример:** Изменить статус пользователя 'anna' на 'active'.
    ```sql
    UPDATE Users
    SET status = 'active'
    WHERE username = 'anna';
    ```
    
- **Ключевые слова:**
    - SET: Указывает, какие столбцы и на какие значения нужно обновить.
    - WHERE: **Обязательный фильтр**, который определяет, **какие именно строки** нужно обновить.
    **ВНИМАНИЕ:** Если пропустить WHERE, команда обновит **ВСЕ** строки в таблице!
### 4. DELETE

- **Назначение:** **Удаляет** существующие записи из таблицы.
- **Базовый синтаксис:**

    ```sql
    DELETE FROM table_name
    WHERE [условие];
    ```
- **Пример:** Удалить всех пользователей со статусом 'banned'.
    ```sql
    DELETE FROM Users
    WHERE status = 'banned';
    ```
    
- **Ключевые слова:**
    - FROM: Указывает, из какой таблицы удалять.
    - WHERE: **Обязательный фильтр**, который определяет, **какие именно строки** нужно удалить.
    **ВНИМАНИЕ:** Если пропустить WHERE, команда удалит **ВСЕ** строки в таблице!
### Итог для запоминания (CRUD)
Эти четыре команды соответствуют акрониму **CRUD**:
- **C**reate (Создать) → INSERT
- **R**ead (Прочитать) → SELECT
- **U**pdate (Обновить) → UPDATE
- **D**elete (Удалить) → DELETE

==Что такое JOIN? Какие типы JOIN вы знаете?==

**JOIN** (соединение) — это операция в SQL, которая позволяет **комбинировать строки из двух или более таблиц** на основе связанного между ними столбца.

### Основные типы JOIN

#### 1. INNER JOIN (Внутреннее соединение)
- **Суть:** **Возвращает только те строки, для которых есть совпадения в обеих таблицах.** Это "пересечение" двух множеств.
- **Когда использовать:** Когда вам нужны только связанные данные. Например, "показать всех пользователей, которые сделали заказ".
- **Пример:**

    ```sql
    SELECT u.name, o.product
    FROM Users u
    INNER JOIN Orders o ON u.id = o.user_id;
    ```

#### 2. LEFT JOIN (Левое внешнее соединение)

- **Суть:** **Возвращает ВСЕ строки из левой таблицы** (та, что после FROM) и совпавшие строки из правой. Если совпадения нет, столбцы правой таблицы будут заполнены NULL.
- **Когда использовать:** Когда нужно получить все данные из основной таблицы, даже если для них нет связанных данных. Например, "показать всех пользователей и их заказы, если они есть".
- **Пример:**

    ```sql
    SELECT u.name, o.product
    FROM Users u
    LEFT JOIN Orders o ON u.id = o.user_id;
    ```

#### 3. RIGHT JOIN (Правое внешнее соединение)

- **Суть:** **Возвращает ВСЕ строки из правой таблицы** (та, что после JOIN) и совпавшие строки из левой. Полная противоположность LEFT JOIN.
- **Когда использовать:** Редко используется, так как почти всегда можно переписать запрос через LEFT JOIN, что более читаемо. Пример: "показать все заказы и имена пользователей, которые их сделали".
- **Пример:**

    ```sql
    SELECT u.name, o.product
    FROM Users u
    RIGHT JOIN Orders o ON u.id = o.user_id;
    ```

#### 4. FULL OUTER JOIN (Полное внешнее соединение)

- **Суть:** **Возвращает ВСЕ строки из ОБЕИХ таблиц.** Если для строки из одной таблицы нет совпадения в другой, недостающие столбцы заполняются NULL. Это объединение результатов LEFT и RIGHT JOIN.
- **Когда использовать:** Когда нужно увидеть все данные из обеих таблиц, независимо от наличия связей.
- **Пример:**

    ```sql
    SELECT u.name, o.product
    FROM Users u
    FULL OUTER JOIN Orders o ON u.id = o.user_id;
    ```

#### 5. CROSS JOIN (Перекрестное соединение)

- **Суть:** Возвращает **декартово произведение** двух таблиц. Каждая строка из первой таблицы соединяется с каждой строкой из второй. Условие ON не используется.
- **Когда использовать:** Редко, в основном для генерации тестовых данных или всех возможных комбинаций.
- **Пример:**

    ```sql
    SELECT u.name, o.product
    FROM Users u
    CROSS JOIN Orders o;
    ```
- **Результат:** 12 строк (3 пользователя * 4 заказа).

==Как работают транзакции в SQL?==
**Транзакция** — это последовательность из одной или нескольких SQL-операций, которые выполняются как **единое, неделимое целое**.

### Основные команды для управления транзакциями
#### 1. BEGIN TRANSACTION (или START TRANSACTION)
- **Назначение:** Явно **начинает** новую транзакцию. Все последующие SQL-команды до COMMIT или ROLLBACK будут считаться частью этой транзакции.
#### 2. COMMIT
- **Назначение:** **Успешно завершает** транзакцию и **сохраняет все изменения** в базе данных навсегда. После COMMIT изменения становятся видны другим пользователям и транзакциям.
- Это точка невозврата.
#### 3. ROLLBACK
- **Назначение:** **Отменяет** (откатывает) все изменения, сделанные с начала транзакции. База данных возвращается в исходное состояние.
- Используется при возникновении ошибки или когда нужно принудительно отменить операцию.
### Как это работает на практике? (Пример)
Представим тот же банковский перевод.

```sql
-- 1. Начинаем транзакцию
BEGIN TRANSACTION;

-- 2. Списываем деньги со счета A (id=1)
UPDATE Accounts
SET balance = balance - 100
WHERE account_id = 1;

-- 3. Зачисляем деньги на счет B (id=2)
UPDATE Accounts
SET balance = balance + 100
WHERE account_id = 2;

-- Проверяем, что все прошло хорошо.
-- Если произошла ошибка (например, у счета 1 не хватило денег),
-- мы бы выполнили ROLLBACK.
-- Если все успешно:

-- 4. Фиксируем изменения
COMMIT;
```

**Что произойдет при сбое?**  
Если сервер отключится после выполнения первой команды UPDATE, но до COMMIT, то при перезапуске СУБД автоматически выполнит ROLLBACK для этой незавершенной транзакции. Баланс счета 1 останется прежним.

Транзакция в SQL — это группа операций, выполняемых по принципу "всё или ничего". Она нужна для обеспечения целостности данных при многошаговых изменениях. Управляется тремя командами: BEGIN начинает транзакцию, COMMIT сохраняет все изменения, если они успешны, а ROLLBACK отменяет все изменения в случае ошибки. Этот механизм является практической реализацией свойств ACID, гарантируя надежность работы с базой данных.

==Расскажи про уровни изолированности транзакций==

**Изолированность** (Isolation) — это свойство 'I' из ACID. Оно определяет, насколько одна транзакция "защищена" от изменений, которые вносят другие, параллельно выполняющиеся транзакции.

**Проблема:** Когда несколько пользователей (транзакций) одновременно работают с одними и теми же данными, могут возникнуть **аномалии чтения** — ситуации, когда одна транзакция видит "грязные", неактуальные или противоречивые данные из-за вмешательства другой.

**Решение:** Уровни изолированности — это набор правил, которые определяют, какие аномалии разрешены, а какие — нет. Это **компромисс между производительностью и согласованностью данных**. Чем выше уровень изоляции, тем надежнее, но медленнее работает система (из-за блокировок).
### Три основные аномалии чтения
Чтобы понять уровни, нужно сначала понять проблемы, которые они решают:
1. **"Грязное" чтение (Dirty Read)**
    
    - **Что это:** Транзакция A читает данные, которые были изменены транзакцией B, но **еще не были зафиксированы** (COMMIT). Если B откатится (ROLLBACK), то A будет работать с несуществующими данными.
    - **Пример:** Транзакция B повышает зарплату сотруднику на 10%. Транзакция A читает эту новую зарплату для отчета. Затем B откатывается. В отчете A теперь неверные данные.
2. **Неповторяющееся чтение (Non-Repeatable Read)**
    
    - **Что это:** В рамках одной транзакции A происходит повторное чтение одной и той же строки, и результат оказывается разным. Это происходит, потому что транзакция B успела **изменить (UPDATE) или удалить (DELETE)** эту строку и зафиксировать изменения.
    - **Пример:** Транзакция A читает цену товара — 100 руб. Затем транзакция B обновляет цену на 120 руб. и делает COMMIT. Транзакция A снова читает цену того же товара и видит уже 120 руб. Данные внутри одной транзакции "поплыли".
3. **"Фантомное" чтение (Phantom Read)**
    
    - **Что это:** В рамках одной транзакции A происходит повторное выполнение запроса с одним и тем же условием WHERE, и количество строк в выборке меняется. Это происходит, потому что транзакция B успела **добавить (INSERT)** новые строки, которые подходят под это условие.
    - **Пример:** Транзакция A считает количество сотрудников в отделе — их 10. Затем B добавляет нового сотрудника в этот отдел и делает COMMIT. Транзакция A снова выполняет тот же подсчет и получает 11. Появилась строка-"фантом".
        
### Четыре уровня изолированности (от слабого к сильному)

#### 1. Read Uncommitted (Чтение незафиксированных данных)

- **Что делает:** Самый низкий уровень. Разрешает читать даже незафиксированные изменения других транзакций.
- **Защита:** Не защищает ни от чего.
- **Возможные аномалии:** Dirty Read, Non-Repeatable Read, Phantom Read.
- **Когда используется:** Практически никогда, так как слишком опасен. Только для задач, где точность не важна (например, грубый подсчет какой-то статистики).
#### 2. Read Committed (Чтение зафиксированных данных)

- **Что делает:** Транзакция видит только те данные, которые были зафиксированы до ее начала, или изменения, внесенные ею самой.
- **Защита:** **Предотвращает "Грязное" чтение (Dirty Read).**
- **Возможные аномалии:** Non-Repeatable Read, Phantom Read.
- **Когда используется:** **Это уровень по умолчанию** для большинства СУБД (PostgreSQL, Oracle, MS SQL Server). Хороший баланс между производительностью и согласованностью.
#### 3. Repeatable Read (Повторяемое чтение)

- **Что делает:** Гарантирует, что если транзакция прочитала строку, то эта строка не изменится до конца транзакции. СУБД блокирует прочитанные строки от изменений (UPDATE, DELETE) другими транзакциями.
- **Защита:** **Предотвращает Dirty Read и Non-Repeatable Read.**
- **Возможные аномалии:** Phantom Read (другие транзакции все еще могут добавлять новые строки).
- **Когда используется:** Когда важно, чтобы данные, с которыми работает длинная транзакция, оставались неизменными. **Уровень по умолчанию в MySQL (InnoDB).**
#### 4. Serializable (Сериализуемый)

- **Что делает:** Самый строгий уровень. Гарантирует, что результат параллельного выполнения транзакций будет таким же, как если бы они выполнялись последовательно, одна за другой.
- **Защита:** **Предотвращает все аномалии:** Dirty Read, Non-Repeatable Read и Phantom Read.
- **Возможные аномалии:** Нет.
- **Когда используется:** В системах с высочайшими требованиями к целостности данных (финансовые, банковские операции), где производительность не является главным приоритетом.

==Как реализовать блокировки в SQL?==
**Блокировка** — это механизм, который база данных использует для **управления одновременным доступом** к данным
### Два подхода к реализации блокировок
Разработчик может работать с блокировками двумя способами:
1. **Неявно (Автоматически):** В 95% случаев вам не нужно ничего делать. База данных сама автоматически накладывает блокировки в соответствии с выбранным уровнем изоляции транзакций. Когда вы делаете UPDATE или DELETE, СУБД сама блокирует нужные строки до конца транзакции.
2. **Явно (Вручную):** В некоторых специфических случаях автоматических блокировок недостаточно. Тогда разработчик может вручную запросить блокировку с помощью специальных SQL-команд.

### Типы явных блокировок

#### 1. Пессимистическая блокировка (Pessimistic Locking)

- **Идея:** "Я предполагаю, что кто-то может помешать мне, поэтому я заблокирую ресурс сразу, как только он мне понадобится".
- **Реализация:** Вы явно блокируете строки в момент их чтения, чтобы никто другой не мог их изменить до окончания вашей транзакции.
- **Основная команда:** SELECT ... FOR UPDATE
#### 2. Оптимистическая блокировка (Optimistic Locking)

- **Идея:** "Я надеюсь, что никто мне не помешает. Я просто проверю перед сохранением, не изменил ли кто-то данные, пока я с ними работал".
- **Реализация:** Это не SQL-команда, а паттерн, реализуемый на уровне приложения. В таблицу добавляется колонка version (или timestamp).
    1. Приложение читает строку вместе с ее версией (например, version = 5).
    2. Выполняет какие-то вычисления.
    3. При сохранении выполняет UPDATE ... WHERE id = ? AND version = 5. В SET также инкрементирует версию (SET version = version + 1).
    4. Если UPDATE затронул 0 строк, значит, кто-то другой уже обновил данные (версия стала 6). Транзакцию нужно откатить и попробовать снова.

### Взаимная блокировка (Deadlock)
- **Что это:** Ситуация, когда Транзакция А ждет ресурс, заблокированный Транзакцией Б, а Транзакция Б ждет ресурс, заблокированный Транзакцией А.
- **Пример:**
    1. Транзакция А блокирует Счет №1.
    2. Транзакция Б блокирует Счет №2.
    3. Транзакция А пытается заблокировать Счет №2 (ждет, пока Б его освободит).
    4. Транзакция Б пытается заблокировать Счет №1 (ждет, пока А его освободит).
        
- **Результат:** Обе транзакции будут ждать вечно.
- **Решение СУБД:** База данных сама обнаруживает такие "циклы ожидания" и принудительно завершает одну из транзакций с ошибкой, позволяя другой продолжиться.
- **Как избежать:** Всегда блокировать ресурсы **в одном и том же порядке** во всех частях приложения (например, всегда сначала блокировать счет с меньшим id).

Реализовать блокировки в SQL можно двумя способами: неявно и явно. Неявно — это когда СУБД сама управляет блокировками в рамках уровней изоляции.
Явная реализация — это пессимистическая блокировка, чаще всего с помощью команды **SELECT ... FOR UPDATE**. Она используется для предотвращения "гонок состояний" в операциях типа "прочитай-измени-запиши". Команда читает строку и немедленно ставит на нее эксклюзивную блокировку, заставляя другие транзакции ждать ее завершения.
Главная опасность при использовании явных блокировок — это возникновение **взаимных блокировок (deadlocks)**, которых можно избежать, если всегда захватывать ресурсы в строго определенном порядке.

==Что такое представления (views)? Зачем они нужны?==
**Представление (View)** — это сохраненный в базе данных запрос, который работает как виртуальная таблица. Оно не хранит данные, а динамически извлекает их из реальных таблиц в момент обращения.

### Зачем они нужны? (Основные преимущества)
#### 1. Упрощение сложных запросов
Это основная причина их использования. Если у вас есть сложный SELECT с множеством JOIN-ов, который используется в разных частях приложения, вы можете "упаковать" его в представление.

**Было (сложно и повторяется везде):**
```sql
SELECT
    u.username,
    u.registration_date,
    p.product_name,
    p.price
FROM Users u
JOIN Orders o ON u.id = o.user_id
JOIN Products p ON o.product_id = p.id
WHERE u.status = 'active';
```

**Стало (просто и чисто):**

```sql
-- 1. Создаем представление один раз
CREATE VIEW ActiveUserPurchases AS
SELECT
    u.username,
    u.registration_date,
    p.product_name,
    p.price
FROM Users u
JOIN Orders o ON u.id = o.user_id
JOIN Products p ON o.product_id = p.id
WHERE u.status = 'active';

-- 2. Используем его где угодно
SELECT * FROM ActiveUserPurchases WHERE price > 1000;
```

#### 2. Безопасность и контроль доступа

Представления позволяют предоставить пользователям доступ не ко всей таблице, а только к определенным данным.

- **Ограничение по столбцам:** Вы можете скрыть конфиденциальные столбцы (например, зарплаты, личные данные).

    ```sql
    -- Показываем только публичную информацию о сотрудниках
    CREATE VIEW PublicEmployeeInfo AS
    SELECT employee_id, full_name, department
    FROM Employees;
    ```
    
- **Ограничение по строкам:** Вы можете показать пользователю только те строки, которые ему разрешено видеть (например, менеджер видит только своих подчиненных).

    ```sql
    CREATE VIEW ManagerTeamView AS
    SELECT *
    FROM Employees
    WHERE manager_id = CURRENT_USER_ID(); -- (условный пример)
    ```
#### 3. Логическая независимость данных

Представление создает стабильный "API" к вашим данным. Вы можете изменять структуру базовых таблиц (например, разделить одну таблицу на две), но при этом сохранить старое представление. Приложения, которые работали со старой структурой через это представление, продолжат работать без изменений.

- **Пример:** Вы решили разбить таблицу Users на UserInfo и UserContacts. Вы можете создать VIEW Users που θα JOIN-ить эти две таблицы, и для старых приложений ничего не изменится.
### Типы представлений

Основное деление — на обновляемые и необновляемые.
#### 1. Обновляемые представления (Updatable Views)

Это простые представления, через которые можно изменять данные в базовой таблице с помощью команд INSERT, UPDATE, DELETE.

**Условия (в общем случае):**

- Представление основано на **одной** таблице.
- Не содержит агрегатных функций (COUNT(), SUM(), и т.д.).
- Не содержит GROUP BY, DISTINCT, UNION.
#### 2. Необновляемые представления (Read-Only Views)

Это сложные представления (с JOIN-ами, агрегацией и т.д.), которые можно использовать только для чтения (SELECT). База данных не может однозначно определить, как UPDATE запроса к такому представлению должен изменить данные в исходных таблицах.

В общем:
**Основные цели его использования:**
1. **Упрощение:** Скрыть сложные JOIN-ы и вычисления за простым именем.
2. **Безопасность:** Предоставить доступ только к разрешенным столбцам и строкам.
3. **Независимость:** Создать стабильный интерфейс к данным, который не ломается при изменении структуры базовых таблиц.»

==Что такое хранимые процедуры?==

**Хранимая процедура** — это именованный блок SQL-кода, который сохранен прямо в базе данных. Это как написать скрипт или функцию, но на языке базы данных, и сохранить ее там же, где лежат данные.
### Зачем они нужны? (Основные преимущества)

1. **Производительность:**
    - **Уменьшение сетевого трафика:** Вместо отправки 10 SQL-запросов по сети, приложение отправляет один короткий вызов процедуры. Это особенно критично в высоконагруженных системах.
    - **Предварительная компиляция:** Когда вы создаете процедуру, база данных анализирует ее, оптимизирует и сохраняет "план выполнения". При последующих вызовах она работает быстрее, пропуская этап парсинга и планирования.
2. **Безопасность:**
    - Это очень мощный инструмент для контроля доступа. Вы можете запретить пользователю прямой доступ к таблицам (SELECT, UPDATE), но дать ему право на выполнение (EXECUTE) процедуры. Таким образом, пользователь может изменять данные только строго определенным, безопасным способом.
3. **Повторное использование и согласованность (DRY - Don't Repeat Yourself):**
    - Сложная бизнес-логика (например, регистрация нового клиента, которая затрагивает 5 таблиц) инкапсулируется в одном месте. Разные приложения или разные части одного приложения могут вызывать одну и ту же процедуру, гарантируя, что логика будет выполнена одинаково.
4. **Абстракция:**
    - Приложение-клиент не должно знать о сложной структуре базы данных. Оно просто вызывает процедуру register_user('name', 'email'), а что там под капотом — INSERT в 3 таблицы, UPDATE в четвертую и логирование — это уже детали, скрытые в процедуре.

### Минусы и риски (Важно знать)

1. **Привязка к вендору (Vendor Lock-in):** Язык хранимых процедур у каждой СУБД свой (T-SQL у MS SQL Server, PL/pgSQL у PostgreSQL, PL/SQL у Oracle). Перенести процедуры с одной СУБД на другую — это огромная работа.
2. **Сложность тестирования и отладки:** Отлаживать код внутри базы данных гораздо сложнее, чем код на уровне приложения. Инструментарий для этого обычно менее развит.
3. **Версионирование:** Управлять исходным кодом процедур в системах контроля версий (как Git) сложнее, чем кодом приложения.
4. **Смешение логики:** Размещение бизнес-логики в базе данных считается некоторыми архитекторами "антипаттерном", так как это размывает границы между слоем данных и слоем бизнес-логики.

**Хранимая процедура** — это именованный блок SQL-кода, сохраненный на сервере базы данных. Ее основная цель — инкапсулировать сложную бизнес-логику.

**Ключевые преимущества:**

- **Производительность** за счет уменьшения сетевого трафика и кэширования плана выполнения.
- **Безопасность**, так как можно давать права на выполнение процедуры, а не на доступ к таблицам.
- **Повторное использование** кода.

**Основные недостатки:**
- Привязка к конкретной СУБД и сложность миграции.
- Трудности в отладке и версионировании.

|**Характеристика**|**Представление (View)**|**Процедура (Stored Procedure)**|
|---|---|---|
|**Главный глагол**|Видеть (Select)|Делать (Do/Execute)|
|**Логика (IF/ELSE)**|Нет (только внутри CASE в SQL)|Да, полноценное программирование|
|**Принимает параметры?**|Нет|Да|
|**Возвращает результат**|Всегда набор строк (таблица)|Может ничего не вернуть, может вернуть число, может набор строк|
|**Использование**|Внутри `FROM` или `JOIN`|Командой `CALL` / `EXEC`|
==Как оптимизировать SQL запросы?==
Прежде чем что-то менять, нужно понять, где проблема. Правильный подход — это не гадать, а измерять.

1. **Используйте EXPLAIN (или EXPLAIN ANALYZE)**: Это самая важная команда. Она показывает **план выполнения запроса** — то, как именно база данных собирается выполнять ваш SQL-код.
    
2. **Ищите "красные флаги" в плане:**
    
    - **Full Table Scan (или Seq Scan в PostgreSQL):** Самый главный враг. Означает, что база данных вынуждена прочитать всю таблицу от начала до конца, чтобы найти нужные строки.
    - **High Cost / High Row Count:** План показывает оценочную "стоимость" операции и количество строк, которое, по его мнению, придется обработать. Большие цифры указывают на узкое место.
    - **Using filesort:** База данных не смогла использовать индекс для сортировки и вынуждена делать это в памяти или на диске, что очень медленно.
### Ключевые техники оптимизации (Что конкретно делать?)

#### 1. Правильное использование индексов (80% успеха)

Это самый эффективный способ оптимизации. Индексы — это первое, что нужно проверять.

- **Индексируйте столбцы в WHERE:** Любой столбец, по которому вы часто фильтруете данные, должен быть проиндексирован.
- **Индексируйте столбцы для JOIN:** Столбцы, по которым вы соединяете таблицы (foreign keys), должны быть проиндексированы в обеих таблицах.
- **Индексируйте столбцы для ORDER BY:** Это позволяет базе данных не сортировать результат "на лету", а сразу брать данные в нужном порядке из индекса.
- **Используйте составные (Composite) индексы:** Если вы часто фильтруете по нескольким столбцам (WHERE country = 'RU' AND city = 'Moscow'), создайте один индекс на оба столбца (country, city). **Порядок столбцов в индексе важен!**
- **Не переусердствуйте:** Каждый индекс замедляет операции записи (INSERT, UPDATE). Индексируйте только то, что действительно нужно.
#### 2. Написание "умных" запросов

Иногда проблема не в отсутствии индекса, а в том, что запрос написан так, что база данных **не может** его использовать.

- **Избегайте SELECT *:** Всегда перечисляйте только те столбцы, которые вам нужны. Это уменьшает объем передаваемых данных и позволяет использовать "покрывающие индексы" (когда все нужные данные есть в самом индексе).
- **Делайте условия "SARGable"** (Search Argument Able): Пишите условия так, чтобы СУБД могла использовать по ним индекс.
    
    - **Плохо (не SARGable):** WHERE YEAR(order_date) = 2023 — применение функции к столбцу не дает использовать индекс.
    - **Хорошо (SARGable):** WHERE order_date >= '2023-01-01' AND order_date < '2024-01-01'
    - **Плохо:** WHERE notes LIKE '%error%' — поиск по подстроке с wildcard в начале не использует индекс.
    - **Хорошо:** WHERE notes LIKE 'error%' — поиск по префиксу использует индекс.
        
- **Используйте UNION ALL вместо UNION**, если уверены, что дубликатов нет. UNION выполняет дополнительную работу по поиску и удалению дублей.
- **Предпочитайте EXISTS вместо IN** для подзапросов, возвращающих много строк. EXISTS останавливается, как только находит первое совпадение, в то время как IN часто материализует весь список из подзапроса.
#### 3. Работа со структурой данных

- **Выбирайте правильные типы данных:** Не используйте VARCHAR(255) для хранения статуса из 5 символов. Чем меньше тип данных, тем компактнее таблица и индексы, и тем быстрее они работают.
- **Денормализация (контролируемая):** Иногда для очень частых и тяжелых запросов на чтение имеет смысл пойти на денормализацию — добавить избыточные данные в таблицу, чтобы избежать дорогостоящих JOIN-ов. Это осознанный компромисс.
#### 4. Поддержание базы данных в "форме"

- **Обновляйте статистику:** Оптимизатор запросов строит план на основе статистики о распределении данных в таблицах. Если статистика устарела, план может быть неэффективным. Регулярно запускайте ANALYZE (или аналогичную команду).
### Итог для собеседования (Ваш план действий)

«Если мне нужно оптимизировать SQL-запрос, я буду действовать системно:

1. **Сначала я проанализирую план его выполнения с помощью EXPLAIN ANALYZE**. Моя цель — найти самые "дорогие" операции, в первую очередь — полное сканирование таблиц (Full Table Scan).
2. **Проверю индексы.** В 80% случаев проблема решается добавлением или исправлением индекса на столбцы из WHERE, JOIN или ORDER BY.
3. **Перепишу запрос, если это необходимо.** Я проверю, что все условия WHERE являются SARGable, то есть не содержат функций на индексированных столбцах, и что я не запрашиваю лишние данные через SELECT *.
4. **Если это не помогло, я посмотрю на более общие вещи:** актуальность статистики в БД, структуру таблиц и возможность денормализации.

==Что такое NoSQL базы данных? В чем их преимущества и недостатки по сравнению с реляционными базами данных?==

## Проблемы, которые решают NoSQL БД

1. **Масштабирование по горизонтали**
    
    - В SQL обычно проще масштабировать «вглубь» (более мощный сервер).
    - NoSQL изначально строились так, чтобы легко добавлять новые узлы в кластер (sharding, репликация) и работать на сотнях серверов.  
        → Решение проблемы **big data** и высокой нагрузки.
   2. **Гибкая схема (schema-less)**
    
    - В SQL нужно заранее описывать таблицы, типы полей, связи.
    - В NoSQL можно хранить документы разной структуры (JSON в MongoDB, ключ-значение в Redis и т. д.).  
        → Удобно для быстро меняющихся данных и прототипирования.
3. **Высокая скорость при больших объёмах**
    
    - Для некоторых задач SQL слишком медленный (например, обработка миллиардов логов).
    - NoSQL заточены под быстрые операции вставки/чтения с упрощённой логикой транзакций.  
        → Решают проблему **реального времени** (real-time аналитика, IoT, логирование).
4. **Работа с полуструктурированными и неструктурированными данными**
    
    - Реляционные базы плохо подходят для документов, JSON, графов, бинарных объектов.
    - NoSQL предлагает специализированные модели:
        - документные (MongoDB, CouchDB),
        - графовые (Neo4j),
        - колоночные (Cassandra, HBase),
        - ключ-значение (Redis).  
            → Решают проблему **разнообразия данных**.
5. **Ограничения ACID в пользу BASE**
    
    - В SQL при больших масштабах тяжело сохранять строгую согласованность (ACID).
    - Многие NoSQL используют модель **BASE** (Basically Available, Soft state, Eventually consistent).  
        → Это решает проблему высокой доступности в распределённых системах (CAP-теорема: жертвуют строгой консистентностью ради доступности и масштабируемости).

## 1 Масштабирование по горизонтали (Horizontal Scaling)

### В реляционных БД (SQL)

- Обычно масштабирование идёт **вертикальное**:  
    добавляем больше CPU, RAM, быстрый диск → база обслуживает больше запросов
- Но есть предел: сервер нельзя «раздувать» бесконечно.
- Горизонтальное масштабирование (sharding/репликация) в классических SQL-БД есть, но оно сложное и не всегда эффективно (например, joins по шардам становятся проблемой).
### В NoSQL

- NoSQL-системы изначально проектировались так, чтобы данные **легко резались на части (шарды)** и раздавались по кластерам.
- При росте нагрузки можно просто добавить ещё серверов:
    - MongoDB, Cassandra, Couchbase автоматически распределяют данные и запросы,
    - клиенту часто всё равно, где физически лежит запись.
- Это удобно для **web-приложений, социальных сетей, big data**, где нагрузка растёт быстрее, чем «железо».
👉 Итого: **NoSQL решает проблему масштабирования, где SQL начинает «упираться» в ограничения одного сервера.**
## 3 Высокая скорость при больших объёмах

### В реляционных БД (SQL)

- Каждая операция обычно проходит через механизм транзакций (ACID):  
    → блокировки, логи, индексы.
- Это обеспечивает консистентность, но замедляет работу при **миллионах простых вставок/чтений в секунду**.
- Пример: логирование событий в реальном времени (миллионы событий в секунду) — SQL просто «задохнётся».
### В NoSQL

- NoSQL оптимизированы под **простые, быстрые операции**:
    - Redis (ключ-значение) может отдавать миллионы запросов/сек.
    - Cassandra и HBase позволяют быстро писать огромные объёмы данных без сложных блокировок.
    - MongoDB быстро работает с JSON-документами без затрат на жёсткие JOIN’ы.
- Механизм ACID часто упрощён или заменён моделью BASE (eventual consistency):  
    → вместо строгой гарантии «всё сразу консистентно», допускается, что данные могут «дойти» до согласованного состояния чуть позже, зато система не тормозит.

👉 Итого: **NoSQL жертвует частью «строгости» SQL, чтобы добиться скорости на огромных объёмах данных.**

### Недостатки NoSQL (по сравнению с SQL)

#### 1. Ослабленные гарантии консистентности.
Это **главный компромисс**. Вместо строгой модели **ACID**, большинство NoSQL баз данных предлагают модель **BASE** (Basically Available, Soft state, **Eventual consistency**).
- **"Eventual Consistency" (Консистентность в конечном счете):** Означает, что после записи данных система не гарантирует, что вы сразу же сможете прочитать эти изменения со всех узлов. Существует задержка, пока данные реплицируются по кластеру. Для банковской системы это неприемлемо, а для лайка в социальной сети — вполне.
- **SQL:** Обеспечивает строгую, немедленную консистентность (ACID).
#### 2. Отсутствие JOIN-ов
В большинстве NoSQL баз нет операции JOIN. Предполагается, что вы будете хранить связанные данные вместе (денормализация). Если вам все же нужно "соединить" данные из разных коллекций, это придется делать на стороне вашего приложения, что медленно и сложно.
#### 3. Отсутствие единого языка запросов
Нет единого стандарта, как SQL. У MongoDB свой язык запросов, у Cassandra — свой (CQL), у Redis — свой набор команд. Это усложняет переход между разными системами.
#### 4. Сложность для сложных запросов
Выполнить сложный аналитический запрос с агрегацией по нескольким сущностям в NoSQL базе данных гораздо сложнее, чем в SQL. SQL для этого подходит идеально.


==Какие NoSQL базы данных вы знаете?==

### 1. Документо-ориентированные (Document Stores)

- **Модель:** Хранят данные в виде гибких, JSON-подобных документов. Каждый документ — самодостаточный объект.
#### MongoDB
- **Что это?** Самая популярная документо-ориентированная база данных. Де-факто стандарт в этой категории.
- **Ключевые особенности:**
    - Очень гибкая схема данных (документы в одной коллекции могут иметь разный набор полей).
    - Мощный язык запросов (MQL), поддерживающий фильтрацию по вложенным полям и агрегации.
    - Поддержка вторичных индексов для ускорения поиска.
- **Когда использовать?** Веб-приложения, каталоги товаров, системы управления контентом, профили пользователей.
#### Elasticsearch
- **Что это?** В первую очередь — это распределенный поисковый и аналитический движок, но в его основе лежит документо-ориентированная база данных.
- **Ключевые особенности:**
    - **Полнотекстовый поиск:** Его главная "суперсила". Невероятно быстрый и умный поиск по тексту.
    - Мощные возможности для аналитики и агрегации данных в реальном времени.
    - Горизонтальная масштабируемость и отказоустойчивость.
- **Когда использовать?** Поиск по сайту, сбор и анализ логов (ELK/EFK Stack), мониторинг приложений, бизнес-аналитика.
### 2. Ключ-Значение (Key-Value Stores)
- **Модель:** Самая простая модель. Данные хранятся в виде пар "ключ-значение", как в огромном словаре или хэш-таблице.
#### Redis
- **Что это?** "Швейцарский нож" среди in-memory баз данных. Невероятно быстрый, так как работает в оперативной памяти.
- **Ключевые особенности:**
    - **Скорость:** Операции занимают доли миллисекунды.
    - **Структуры данных:** Поддерживает не только строки, но и списки, множества, хэши, потоки (streams), что делает его очень мощным.
    - **Встроенные фичи:** Pub/Sub (обмен сообщениями), транзакции, опциональная персистентность (сохранение на диск).
- **Когда использовать?** Кэширование, хранение сессий, таблицы лидеров в играх, очереди задач, real-time аналитика.
#### Memcached
- **Что это?** Более старый и простой аналог Redis.
- **Ключевые особенности:**
    - Чистое in-memory хранилище, без персистентности.
    - Только строковые значения, нет сложных структур данных.
    - Многопоточная архитектура (в отличие от однопоточного Redis).
- **Когда использовать?** Исключительно для кэширования, когда не нужны продвинутые возможности Redis.
### 3. Колоночные (Wide-Column Stores)
- **Модель:** Данные хранятся по колонкам, а не по строкам. Оптимизированы для огромных объемов записи и быстрой агрегации данных из конкретных колонок.
#### Apache Cassandra
- **Что это?** Распределенная база данных, спроектированная для обработки гигантских объемов данных с высочайшей доступностью.
- **Ключевые особенности:**
    - **Мастер-архитектура (Masterless):** Нет единой точки отказа. Все узлы равны.
    - **Линейная масштабируемость:** Производительность растет предсказуемо при добавлении новых узлов.
    - **Настраиваемая консистентность:** Вы можете выбирать, насколько строгой должна быть согласованность данных, в обмен на скорость.
- **Когда использовать?** IoT (данные с датчиков), хранение временных рядов (time-series), системы логирования, мессенджеры с огромной нагрузкой.
#### ScyllaDB
- **Что это?** "Кассандра на стероидах". Полностью переписанная на C++ версия Cassandra, API-совместимая с ней.
- **Ключевые особенности:**
    - Значительно более высокая производительность на том же "железе" за счет низкоуровневых оптимизаций.
    - Меньшие задержки (latency).
- **Когда использовать?** Те же сценарии, что и у Cassandra, но когда требуется экстремальная производительность.
### 4. Графовые (Graph Databases)
- **Модель:** Данные хранятся в виде узлов (вершин) и связей (ребер) между ними. Созданы для эффективной работы с сильно связанными данными.
#### Neo4j
- **Что это?** Самая популярная нативная графовая база данных.
- **Ключевые особенности:**
    - **Специализированный язык запросов Cypher:** Очень интуитивный для описания и поиска паттернов в графе.
    - **Высокая производительность для графовых запросов:** Мгновенно находит связи типа "друзья друзей", в то время как в SQL это потребовало бы множества медленных JOIN-ов.
    - Поддержка ACID-транзакций.
- **Когда использовать?** Социальные сети, рекомендательные системы, антифрод-системы (поиск мошеннических схем), управление сетями, графы знаний.
